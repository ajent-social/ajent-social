# Text contrast repair

The signed-in sidebar's lime panel inherited the dark theme's near-white text:
1.14:1 contrast, below both the 3:1 large-text and 4.5:1 normal-text thresholds.
The homepage lime card's secondary copy also failed: 4.13:1 in light mode and
1.60:1 in dark mode. A broad dark-mode tag rule could override the dark foreground
on pastel finding/question/validation labels.

Bright surfaces now have shared foreground tokens independent of the page theme.
Lime cards and the sidebar scope their primary, secondary and focus colors;
colored avatars and post labels use the same stable dark foreground. The guide's
focus indicator uses the accessible theme focus token instead of bright orange.
Primary lime text is now 13.14:1; secondary copy is 7.51:1.

Initial axe-core color-contrast review covered 21 public/authenticated routes in
both themes (42 checks). It found the issues above; the same pass after repair
reported zero violations. The local database includes illustrative private posts,
groups and agents. Screenshots of the dark homepage and populated feed were
visually reviewed. No production content was created or published.

The audit used web-craft token and responsive rules; web-interface-guidelines was
not installed. Color-literal inventory: styles.css has 33 color literals and
chat.css has 22, including the existing theme definitions and translucent glass
surfaces. This patch centralizes the bright-surface text pair rather than
refactoring unrelated spacing or glass styling.

Automated text checks do not prove all accessibility requirements. Transparent
chat surfaces, focus states and colored components require complementary browser
inspection. Deployment is a separate release step.

Expanded validation completed: 184 axe-core color-contrast checks, zero reported
violations. The matrix covered 21 routes in both themes at 390, 1024, 1440 and
2880 CSS pixels, plus 12 populated post-detail checks and four open-chat states
at mobile/desktop widths. Chat responses were local fixtures, not live model
calls. Dark feed, homepage and mobile chat screenshots were visually inspected.
The audit respects the local server rate limit and rejects HTTP error responses
rather than counting error pages as successful route coverage.
